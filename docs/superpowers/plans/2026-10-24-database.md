> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build David's part of Nametags:
- the Postgres + pgvector schema, including the person context (facts and the card);
- the queries behind the setup routes and the context routes;
- the nearest-person queries that the live connection calls.

**Architecture:**
- One SQL file defines the schema.
- A `db/` package holds small functions. Each one takes a psycopg connection and runs a few SQL
  statements.
- A `backend/` FastAPI app serves the setup routes using those functions.
- The context owner's routes (notes, conversation, facts) call the same functions.
- Matching is one SQL query, which returns the nearest two people, each scored by their best
  sample. A pure Python function then decides between *named*, *not sure* and *no match*.

**Tech Stack:** PostgreSQL 17 + pgvector (Docker image `pgvector/pgvector:pg17`), psycopg 3 with
`psycopg_pool`, FastAPI, Pillow, pytest, uv.

**Spec:** `docs/superpowers/specs/2026-10-24-nametags-design.md`. The interfaces come from
`docs/superpowers/plans/2026-10-24-hour0-contract.md` once the contract changes below are applied.

## Person context: small and large

| Your scratchpad/memory slide | In Nametags | Where it lives |
|---|---|---|
| Scratchpad: raw data, one session | The visit transcript | Not in Postgres. It travels as JSON in the End-visit request, and is gone once Gemini has digested it |
| Memory: curated, across sessions | Facts (the large context) | `facts`: one fact per row, only ever added or deleted, never rewritten |
| The digest that's always loaded | The card (the small context) | `people.small_context`, read at recognition time with no Gemini call |

- **The whole large context goes into every Gemini call.**
  - One person's facts are roughly 2–5k tokens, and a 30-minute transcript is roughly 5–6k. Both
    are my estimates.
  - Google's page for Gemini 2.0 Flash lists 1,048,576 input tokens, so one call uses about 1%.
    Even a model limited to 200k tokens would use about 7%.
  - So there's no retrieval step and no embeddings on facts. `WHERE person_id = …` *is* the
    retrieval.
  - Add an embedding column only if facts per person reach the thousands, or if questions across
    people are needed. Both are out of scope.
- **The small context is limited by the reader, not the model:** at most 300 characters (two
  short sentences, about 75 tokens), enforced by a CHECK.
- **The flow:** read the facts (a short transaction), call Gemini (holding no connection), then
  `save_context` (one transaction that writes the card and the new facts). A reply that breaks the
  limits changes nothing.

## What your courses decide here

The citations point to the study notes in `Second Mind/03 Courses/`.

| Course note | What it says | What it decides here |
|---|---|---|
| CSCI 300 L02 Relations and keys | superkey → candidate key → primary key; a foreign key must point at a key; a relation is an unordered set | Every table gets a surrogate `id`. Declared candidate keys: `file_path`, `audio_path`, (name, relationship) ignoring case, (`photo_id`, `person_id`), and (`person_id`, fact text). Every list and match query has an ORDER BY. |
| CSCI 300 L13 ER model | redundant copies "can disagree" | `face_count` and `has_voice` are computed, never stored. The card is the one deliberate stored copy: rebuilding it needs a network call, and the Live page must work offline. It's written in the same transaction as its facts. |
| CSCI 300 L14 ER constraints to tables | a many-to-one relationship folds into the "many" table; folding a partial one "needs a NULL" | Face→person is partial, so `person_id` is nullable (`SET NULL`). Voice→person and fact→person are total: `NOT NULL` (`CASCADE`). Face→photo is total: `NOT NULL` + `CASCADE` (the other legal choice would be refusing the delete). A face sample is *not* a weak entity, because it has its own key. |
| CSCI 300 L10 NULLs | a comparison with NULL is "Maybe"; WHERE keeps only what is definitely True | An unlabelled face has `person_id` NULL. Two Postgres NULL rules matter here (they're Postgres facts, not quotes from the note): GROUP BY puts all NULLs in one group, so unlabelled faces compete as one "not enrolled" candidate; and UNIQUE treats NULLs as distinct, so a photo can hold any number of unlabelled faces. |
| CSCI 300 L15 | a multivalued attribute gets a table of its own | Samples and facts live in their own tables. |
| CSCI 300 L08–L09 Grouping, aggregates | GROUP BY and aggregate functions | `MIN(distance)` per person. Under a LEFT JOIN, `COUNT(f.id)`, not `COUNT(*)`. |
| CSCI 300 L11 Correlation and EXISTS | correlated EXISTS | `has_voice` uses EXISTS, so faces and voices are never joined together and counts can't multiply. |
| CSCI 300 L16–L17 Normalization, BCNF | 1NF means one indivisible value per column; BCNF means every determinant is a superkey | Every table is in BCNF: the only determinants are `id` and the declared unique keys. One fact per row is what makes "delete one bad fact" and "the newer fact wins" possible. |
| CSCI 405 L02 Index structures | every index buys lookup speed and pays in insert, delete and space | No extra indexes. The unique indexes already serve the lookups: (`photo_id`, `person_id`) serves "faces in this photo", and the facts index serves "David's facts". |
| CSCI 405 L03 B+ tree indices | B+ trees keep keys sorted for fast lookups | Every PRIMARY KEY and UNIQUE constraint is backed by a B-tree index: ten in this schema. |
| CSCI 405 L06 Query processing costs | a full scan can beat a secondary index outright | Matching is an exact sequential scan. No HNSW or IVFFlat: those are approximate, and could miss the true nearest face. |
| CSCI 426 L04–L05 Retrieval, similarity | in the vector space model, relevance is nearness to the query; cosine compares the angle | Voices use cosine distance. Faces use L2, because dlib's model was trained so that the same person lands within 0.6 Euclidean distance. |
| Interview answer on indexing | "you index for measured query patterns, not on instinct" | Verification runs `EXPLAIN ANALYZE` on 330 faces. |

## Schema

ER diagram in your CSCI 300 notation:

```
┌──────────┐                ┌─────────────┐                  ┌───────┐
│  person  │◀── <depicts> ──│ face_sample │══ <contains> ───▶│ photo │
└──────────┘                └─────────────┘                  └───────┘
   ▲     ▲
   │     └────── <about> ══ ┌──────┐
   │                        │ fact │
   │                        └──────┘
   └────── <of> ══ ┌──────────────┐
                   │ voice_sample │
                   └──────────────┘

══ total participation · ── partial · ▶ "at most one" on that side
```

Relation schemas, with the primary key underlined and `→` marking a foreign key:

```
people(id, name, relationship, small_context, created_at)
       ──
photos(id, file_path, width, height, uploaded_at)
       ──
face_samples(id, photo_id → photos, person_id → people, box_x, box_y, box_width, box_height, model, embedding)
             ──
voice_samples(id, person_id → people, audio_path, model, embedding, created_at)
              ──
facts(id, person_id → people, text, source, created_at)
      ──
```

`db/schema.sql` is applied at every startup, so every statement says `IF NOT EXISTS`. `source`
uses a CHECK rather than an ENUM type, because `CREATE TYPE` has no `IF NOT EXISTS`.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE IF NOT EXISTS people (
    id            integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name          text NOT NULL CHECK (name ~ '\S' AND char_length(name) <= 80),
    relationship  text NOT NULL CHECK (relationship ~ '\S' AND char_length(relationship) <= 40),
    small_context text NOT NULL DEFAULT '' CHECK (char_length(small_context) <= 300),
    created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS people_name_relationship_key
    ON people (lower(btrim(name)), lower(btrim(relationship)));

CREATE TABLE IF NOT EXISTS photos (
    id          integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    file_path   text NOT NULL UNIQUE,
    width       integer NOT NULL CHECK (width > 0),
    height      integer NOT NULL CHECK (height > 0),
    uploaded_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS face_samples (
    id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    photo_id   integer NOT NULL REFERENCES photos (id) ON DELETE CASCADE,
    person_id  integer REFERENCES people (id) ON DELETE SET NULL,  -- NULL = unlabelled
    box_x      integer NOT NULL CHECK (box_x >= 0),
    box_y      integer NOT NULL CHECK (box_y >= 0),
    box_width  integer NOT NULL CHECK (box_width > 0),
    box_height integer NOT NULL CHECK (box_height > 0),
    model      text NOT NULL CHECK (model ~ '\S'),
    embedding  vector(128) NOT NULL CHECK (vector_norm(embedding) > 0),
    UNIQUE (photo_id, person_id)       -- one face per person per photo; NULLs never clash
);

CREATE TABLE IF NOT EXISTS voice_samples (
    id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    person_id  integer NOT NULL REFERENCES people (id) ON DELETE CASCADE,
    audio_path text NOT NULL UNIQUE,
    model      text NOT NULL CHECK (model ~ '\S'),
    embedding  vector(192) NOT NULL CHECK (vector_norm(embedding) > 0),
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS facts (
    id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    person_id  integer NOT NULL REFERENCES people (id) ON DELETE CASCADE,
    text       text NOT NULL CHECK (text ~ '\S' AND char_length(text) <= 300),
    source     text NOT NULL CHECK (source IN ('conversation', 'notes')),
    created_at timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS facts_person_text_key ON facts (person_id, lower(btrim(text)));
```

- **`'\S'`** matches any non-whitespace character, so names made only of spaces, tabs or newlines
  are refused. A blank name would make the app say "That's , your grandson."
- **Zero vectors are refused,** because cosine distance to a zero vector is NaN (not a number).
- **`model`** records which embedder produced each sample, so the backend can refuse to start when
  stored samples came from a different model, such as the fakes.
- **`CREATE TABLE IF NOT EXISTS` never changes a table that already exists.** After editing the
  schema, stop the backend and reset, from the repo folder:
  `docker compose down -v && find data -type f -delete`. That deletes every person, photo and
  recording.

What deleting does:

| Delete | Effect | Why |
|---|---|---|
| A person | Their faces become unlabelled (`SET NULL`). Their voice samples and facts are deleted (`CASCADE`), and the route deletes the audio files. | The face is still in the photo; only its link to the person goes. Voice samples and facts mean nothing without the person, and a recording shouldn't outlive them. |
| A photo | Its faces are deleted (`CASCADE`). | A face exists only inside its photo. |
| One voice sample | The route deletes its audio file after the commit. | It was a bad recording. |
| One fact | Only that row is deleted. The card isn't rewritten: the family edits it, or the next update fixes it. | One bad fact shouldn't touch the rest. |

## Queries

Every value is passed as a psycopg parameter. A `%(x)s::vector` cast turns a Python list of
floats into a pgvector value, so the `pgvector` Python package isn't needed.

**People** (`db/people.py`)

```sql
-- list_people. get_person adds WHERE p.id = %(id)s before GROUP BY.
SELECT p.id, p.name, p.relationship, p.small_context,
       COUNT(f.id) AS face_count,
       EXISTS (SELECT 1 FROM voice_samples v WHERE v.person_id = p.id) AS has_voice
FROM people p
LEFT JOIN face_samples f ON f.person_id = p.id
GROUP BY p.id
ORDER BY p.name, p.id;

-- create_person. A UniqueViolation on people_name_relationship_key becomes Conflict.
INSERT INTO people (name, relationship) VALUES (%(name)s, %(relationship)s) RETURNING id;

-- update_person: a field passed as None keeps its value.
UPDATE people
SET name = COALESCE(%(name)s, name),
    relationship = COALESCE(%(relationship)s, relationship),
    small_context = COALESCE(%(small_context)s, small_context)
WHERE id = %(id)s
RETURNING id;
-- When small_context was given and isn't blank, the family's card is also kept as a note,
-- so the next Gemini rewrite starts from their correction (same transaction):
INSERT INTO facts (person_id, text, source) VALUES (%(id)s, %(small_context)s, 'notes')
ON CONFLICT DO NOTHING;

-- delete_person, in one transaction. The lock waits for any in-flight add_voice or assign_face
-- for this person, and makes later ones fail. No row means "no such person".
SELECT id FROM people WHERE id = %(id)s FOR UPDATE;
SELECT audio_path FROM voice_samples WHERE person_id = %(id)s ORDER BY id;   -- files to delete after the commit
DELETE FROM people WHERE id = %(id)s;    -- the foreign keys unlabel faces and delete voices and facts
```

**Photos and faces** (`db/photos.py`)

```sql
-- save_photo, in one transaction, after checking every box lies inside the photo
INSERT INTO photos (file_path, width, height) VALUES (%(path)s, %(width)s, %(height)s) RETURNING id;
INSERT INTO face_samples (photo_id, box_x, box_y, box_width, box_height, model, embedding)
VALUES (%(photo_id)s, %(x)s, %(y)s, %(w)s, %(h)s, %(model)s, %(embedding)s::vector)
RETURNING id;                                     -- once per detected face

-- assign_face: the column holds one person, so reassigning moves the label, and NULL unlabels it.
-- UniqueViolation (photo_id, person_id) becomes Conflict; ForeignKeyViolation becomes NotFound("person").
UPDATE face_samples SET person_id = %(person_id)s WHERE id = %(face_id)s;

-- list_photos (GET /photos): one statement, so photos and faces come from one snapshot.
-- A photo with no faces gives one row whose face columns are NULL.
SELECT ph.id AS photo_id, ph.width, ph.height,
       f.id AS face_id, f.box_x, f.box_y, f.box_width, f.box_height, f.person_id
FROM photos ph
LEFT JOIN face_samples f ON f.photo_id = ph.id
ORDER BY ph.id, f.id;

-- photo_file (GET /photos/{id}/image)
SELECT file_path FROM photos WHERE id = %(id)s;
```

**Voice** (`db/voice.py`)

```sql
-- add_voice: recording again adds a sample, and matching uses the person's best one
INSERT INTO voice_samples (person_id, audio_path, model, embedding)
VALUES (%(person_id)s, %(path)s, %(model)s, %(embedding)s::vector)
RETURNING id;

-- list_voice (GET /people/{id}/voice)
SELECT id, created_at FROM voice_samples WHERE person_id = %(person_id)s ORDER BY id;

-- delete_voice (DELETE /people/{id}/voice/{voice_sample_id}); the route deletes the file after the commit
DELETE FROM voice_samples WHERE id = %(sample_id)s AND person_id = %(person_id)s RETURNING audio_path;
```

**Person context** (`db/context.py`)

```sql
-- list_facts: the large context, oldest first, so Gemini can let a newer fact win
SELECT id, text, source, created_at FROM facts WHERE person_id = %(person_id)s ORDER BY created_at, id;

-- save_context, in one transaction, after the Gemini call has returned (never during it)
UPDATE people SET small_context = %(small_context)s WHERE id = %(person_id)s RETURNING id;  -- no row: NotFound
INSERT INTO facts (person_id, text, source) VALUES (%(person_id)s, %(text)s, %(source)s)
ON CONFLICT DO NOTHING;                           -- once per new fact; exact repeats are skipped

-- delete_fact (DELETE /people/{id}/facts/{fact_id})
DELETE FROM facts WHERE id = %(fact_id)s AND person_id = %(person_id)s;
```

**Matching** (`db/match.py`)

`{samples}` and `{op}` are filled in from fixed dictionaries using `psycopg.sql`:

```sql
SELECT p.id, p.name, p.relationship, p.small_context,
       MIN(s.embedding {op} %(q)s::vector) AS distance
FROM {samples} s
LEFT JOIN people p ON p.id = s.person_id
GROUP BY p.id
ORDER BY distance, p.id
LIMIT 2;
```

- `{samples}` is `face_samples` or `voice_samples`.
- `{op}` is `<->` (L2 distance) or `<=>` (cosine distance, which is 1 − cosine similarity).
- The query returns the nearest two *people*, each scored by their best sample, with their card.
- All unlabelled faces form one extra group, whose id, name and relationship are NULL. Voice
  samples always have a person.
- `decide()` turns those candidates into one of three outcomes:
  - **`"no_match"`** when there are no candidates, or the nearest distance isn't a finite number
    under the cutoff;
  - **`"not_sure"`** when the nearest group is the unlabelled one, or when the runner-up is within
    `margin` of it;
  - **the nearest `Candidate`** otherwise.
- **Rule for the live layer:** only `"no_match"` lets a face become eligible for "I don't recognize
  this person", after the wait. `"not_sure"` stays silent. Voice never triggers "unknown".
- **The margin** (my call) starts at 0.05 for both faces and voices, and gets tuned together with
  the cutoffs.

## Global Constraints

- **Database:** PostgreSQL 17 + pgvector from `pgvector/pgvector:pg17`.
  - The port is published as `"127.0.0.1:5433:5432"`, so only this laptop can connect. Anyone on
    the event Wi-Fi could otherwise log in with the default password.
- **Connection strings:** user, password and database are all `nametags`. `DATABASE_URL` defaults
  to `postgresql://nametags:nametags@localhost:5433/nametags`. The tests always use
  `TEST_URL = "postgresql://nametags:nametags@localhost:5433/nametags_test"`.
- **Files:** photos and recordings live under `NAMETAGS_DATA` (default `data`).
  - New files are named with `uuid.uuid4().hex`, plus `.jpg`, `.png` or `.wav` taken from the
    decoded format, never from the client's file name.
  - They are written with `open(path, "xb")`, so nothing is ever overwritten.
- **Public repo:** the root `.gitignore` gets `data/` and `.env`. The repo is public, and `.env`
  holds `GEMINI_API_KEY`.
- **Network:** the `db/` functions never call the network. Gemini is called only from the context
  owner's code, and never while a database transaction is open.
- **SQL safety:** every value goes in as a psycopg parameter. Operator and table names come only
  from fixed dictionaries composed with `psycopg.sql`.
- **Embedding sizes:**
  - faces are `vector(128)`, because `face_recognition` always returns 128 numbers;
  - voices are `vector(192)`, for SpeechBrain's `spkrec-ecapa-voxceleb`. Confirm this with the voice
    owner in hour 0.
  - At startup, `check_embedders` refuses a size or model mismatch.
- **Cutoff semantics:** a cutoff is a distance, and a match must be strictly under it.
  - Cosine distance is 1 − cosine similarity, so a similarity threshold *s* becomes the cutoff
    1 − *s*.
  - SpeechBrain's default 0.25 is a similarity, even though its docs call it a distance. That
    makes the cutoff 0.75.
- **Error mapping:**
  - `NotFound` → 404;
  - `Conflict` → 409;
  - `CheckViolation` → 422;
  - `NumericValueOutOfRange` (an id too large for `integer`) is treated as "no such row", so 404.
- **Indexes:** none beyond the primary keys and unique keys.
- **SQL style (from CSCI 300):** uppercase keywords; table aliases without AS.
- **Docker Desktop:** open it from the Dock or Spotlight, never with `open -a` from an agent shell
  (AGENTS.md). An agent executing this plan asks David to open it.
- **Commits:** short messages, with no Co-Authored-By or "Generated with" line. Commit only when
  David says so.

```python
if not candidates:
    return "no_match"
best = candidates[0]
if not (math.isfinite(best.distance) and best.distance < cutoff):
    return "no_match"
if best.person_id is None:
    return "not_sure"
if len(candidates) > 1 and not (candidates[1].distance - best.distance >= margin):
    return "not_sure"
return best
```

| Route | Calls | Errors |
|---|---|---|
| `GET /people` | `list_people` | — |
| `POST /people` → 201 | `create_person` | 409; 422 |
| `PATCH /people/{id}` | `update_person` | 404; 409; 422 |
| `DELETE /people/{id}` → 204 | `delete_person`, then delete the returned audio files after the commit | 404 |
| `POST /photos` → 201 | upright image → `face_embedder.detect_faces` → write file → `save_photo` | 422 unless JPEG or PNG |
| `GET /photos` | `list_photos` | — |
| `GET /photos/{id}/image` | `photo_file` → file response | 404 |
| `POST /faces/{face_id}/assign` → 204 | `assign_face` | 404, naming the face or the person; 409 |
| `POST /people/{id}/voice` → 201 | `check_wav` → `voice_embedder.embed_voice` → write file → `add_voice` | 422 for the wrong format; 404 |
| `GET /people/{id}/voice` | `get_person` (404) → `list_voice` | 404 |
| `DELETE /people/{id}/voice/{voice_sample_id}` → 204 | `delete_voice`, then delete the file after the commit | 404 |

- **Context routes:** `notes`, `conversation`, `GET facts` and `DELETE facts` are the context
  owner's router. It calls Task 5's functions, and `app.include_router` mounts it once it exists.
- **Embedders:** module attributes `face_embedder = FakeFaceEmbedder()` and
  `voice_embedder = FakeVoiceEmbedder()` stand in until the owners' adapters exist; swapping each is
  one line.
- **Startup:** the lifespan reads `DATABASE_URL` (default `DEFAULT_URL`) and `NAMETAGS_DATA`
  (default `data`), opens the pool, and runs
  `check_embedders(conn, face_embedder.spec, voice_embedder.spec)`. On a mismatch it refuses to
  start.
- **Routes** are plain `def` functions, so FastAPI runs them in its thread pool.
- **Order of work inside a route:**
  - the slow work (image decode, embedding) happens before taking a connection;
  - the database calls run inside one `with pool.connection() as conn:` block;
  - if that block raises, the route deletes any file it just wrote;
  - files to remove are deleted only after the commit.
- **Upright photos:** `POST /photos` applies `PIL.ImageOps.exif_transpose` first, and re-encodes
  only when the orientation tag isn't 1. The embedder, the stored file and the width and height
  then all use the same upright pixels.
